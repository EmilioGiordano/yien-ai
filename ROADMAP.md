# ROADMAP

The index for agents: where the project stands and what comes next. Each branch updates its own row as its last commit. Rules are in `AGENTS.md`; behaviour in the ERS; engineering in the plan (absolute paths in `AGENTS.md`).

## Target: MVP

A YIEN that Emilio can use for real work on Windows:

- One window. Projects in a sidebar, vertical tabs per project, and split terminal panes per tab, following the prototype `design/prototipo-navegacion.html`.
- Each pane runs a shell or an agent CLI (Claude Code, Codex, OpenCode) through ConPTY, with correct rendering, input (IME, AltGr), copy and paste, and scrollback.
- Panes split, resize, close, swap and get focused by keyboard and mouse. Command palette.
- Claude Code state detection (working / needs you / idle) with the red mark and the attention counter (RN-01, RN-02).
- The layout and sessions survive a restart.
- `yien --test-control` so every feature is validated in the running app (ADR-21).

This is plan milestones M0–M2, the core of M3 and the Claude part of M4. Phase 0 is cut down to the spikes that decide the stack: S2 (ConPTY) and S1 (GPUI), sized to one night.

## Decisions taken on the way

Record here what a spike or a branch decided, with the branch name. The plan's spike log in `docs/` holds the details.

- `build/workspace-skeleton`: layer-0 crates do not depend on each other. `yien-layout` keeps its own `PaneId` (a `u64` handed out by the tree); mapping it to `yien_proto::PaneId` is the core's job.
- `build/workspace-skeleton`: foothy's `win32.rs` (win32-input-mode encoding) was left out of `yien-input` as the TASK asked. It makes no OS calls, and plan §3.2 places win32-input-mode in `yien-input`, so it should come back there with M1 input, not go to `yien-platform`. Done in `build/tracing-and-input-mode` (`yien_input::win32`).
- `build/workspace-skeleton`: `xtask check-deps` also requires `#![forbid(unsafe_code)]` in every crate root except `yien-pty` and `yien-platform`, limits `yien-proto` to `serde`, and holds layers 0 and 1 to an allowlist of external crates kept in `xtask/src/check_deps.rs` (adding one is a reviewed change).
- `feat/vt-engine`: the engine has no clock. A synchronized update (mode 2026) holds output and replies until it closes; the pane actor calls `flush_sync` once `sync_pending` has been true for `SYNC_UPDATE_TIMEOUT` (150 ms), restarting that timer whenever `sync_generation` changes.
- `feat/vt-engine`: `Frame.cursor` is `None` only when scrolled out of view; a hidden cursor keeps its point (`Cursor::visible` false) so the IME window can follow it (RF-PAN-15).
- `feat/vt-engine`: `osc_scan` treats `OSC 9;<number>;…` as a ConEmu command (`9;4` progress, `9;9` cwd), never as a notification, so it cannot raise a false red mark (RN-02). Only 7-bit `ESC ]`, BEL and `ESC \` are recognised; C1 bytes are UTF-8 continuation bytes in practice.
- `feat/vt-engine`: link detection covers OSC 8, URLs and absolute Windows drive paths; relative and Unix paths are left for later.
- `feat/ui-shell`: ADR-02 taken: the UI is GPUI through the crates.io package `gpui-kit =0.7.1` (bundles gpui and gpui-component), the pin Zenkai builds and runs on this PC. The lock holds `gpui-base`, `gpui-component` and `gpui-kit-assets` at 0.7.1 to match Zenkai. Its tree needs `0BSD` and `bzip2-1.0.6` in the deny licence list and seven unmaintained-crate advisories ignored (listed in `deny.toml`).
- `feat/ui-shell`: the `yien` binary is layer 4 in `check-deps`; it may depend on every layer and nothing depends on it. `yien-ui` owns `run()`, so the binary does not depend on gpui.
- `feat/ui-shell`: the view model (`WorkspaceView`) lives in `yien-ui`, keyed by `yien-proto` ids, and models all five RF-AGE-05 states. The counter counts panes (RF-ATN-03); project heads count tabs.
- `build/tracing-and-input-mode`: logs go to `<data dir>/logs`, where the data dir is `%LOCALAPPDATA%\YIEN` or `$YIEN_DATA_DIR`, not to the state dir that plan §5.4 names, so a throwaway profile redirects them too. Debug builds also log to stderr. `yien-platform` uses `#![deny(unsafe_code)]`, so later OS code can allow `unsafe` per module with a `// SAFETY:` line.
- `build/tracing-and-input-mode`: the log guard is dropped in the callback `yien_ui::run` takes for gpui's `on_app_quit`, because gpui calls `process::exit` at Windows end of session without returning from `run`. `vte` (off) and `alacritty_terminal` (warn) are capped on top of `YIEN_LOG`, since their debug and trace records carry terminal content. The binary logs panics (location and a message capped at 200 chars) before the default hook.
- `feat/ui-shell`: the sumi `shu` red is below WCAG AA on `panel` (4.39:1) and `raised` (4.11:1), where the tab bar and the counter use it (RNF-18). Left as designed, pending a token change.
- `feat/pty-backend`: resizes go through the writer thread with the input (plan §4.1), so `resize` reports only "queued"; an OS resize failure is not surfaced.
- `feat/pty-backend`: end of session is the child's exit (a blocking `wait`; `try_wait` reads exit code 259 as still running), then 100 ms of quiet output measured from the later of the exit and the reader's last wait, capped at 2 s. Both clocks count only time the reader spends waiting in `read`, so the cap does not bound wall time while a consumer is behind; and `Exited` is queued only then, so every byte read before it is delivered first. Bytes that arrive after `Exited` are still forwarded.
- `feat/pty-backend` open: closing a session while the writer is inside a long `write_all` (a large paste into a stalled child) waits for that write; not verified.
- `feat/pty-backend`: `write` never blocks: a full input queue returns the bytes in `PtyError::InputQueueFull`. Dropping the session kills the child.
- `feat/pty-backend`: portable-pty 0.9 loads a `conpty.dll` found on the DLL search path before the kernel32 one. That is the seam for the bundled ConPTY (TBD-05). Until `fix/conpty-load` that search included `PATH`, so on this PC every pane ran tty7's `conpty.dll` and `OpenConsole.exe`, not the system ConPTY. Since then only a `conpty.dll` next to `yien.exe` can be picked up, and nothing ships one.
- `fix/conpty-load` (security): portable-pty 0.9 calls `LoadLibraryW("conpty.dll")` by bare name (`portable-pty-0.9.0/src/win/psuedocon.rs:55`, through `shared_library`) after checking that kernel32 exports ConPTY, and prefers it when found. A bare-name load searches the cwd and every `PATH` folder, so a writable `PATH` folder or a malicious repo used as the cwd could inject code. `yien_platform::dll_search::restrict_dll_search` now runs first in `yien`'s `main`: `SetDefaultDllDirectories(LOAD_LIBRARY_SEARCH_APPLICATION_DIR | LOAD_LIBRARY_SEARCH_SYSTEM32)`, then `SetDllDirectoryW("")`. A failure is logged and the app goes on; neither call fails on Windows 10 or later.
- `fix/conpty-load`, evidence (release builds, throwaway `YIEN_DATA_DIR`, run from the slot's `run/`, modules read with `(Get-Process).Modules` 8 s after start). Before (the slot's previous release build, 10:12, before ba5c236; portable-pty 0.9.0 in the lock throughout): `C:\Users\giord\AppData\Local\Programs\tty7\conpty.dll` loaded, and the pane's host child was `C:\Users\giord\AppData\Local\Programs\tty7\OpenConsole.exe`. After: no `conpty.dll`, the only module outside `C:\Windows` is `yien.exe`, the host child is `C:\Windows\system32\conhost.exe`, and the two module lists differ by that one DLL. The pane's `powershell.exe` runs under the system ConPTY, and `yien-pty`'s tests pass with tty7 removed from `PATH`.
- `fix/conpty-load`: `yien-hook` does not call it. The setting governs run-time `LoadLibrary` only; `yien-hook` loads nothing at run time, and its static imports are system DLLs resolved from System32 before `main` runs, where the call could not help.
- `fix/conpty-load`, follow-up: bundling `conpty.dll` and `OpenConsole.exe` next to `yien.exe` (TBD-05) would bring a newer ConPTY than Windows 10's in-box conhost (passthrough mode, later fixes). The app-dir search keeps that seam open. Not now.
- `fix/conpty-load`, open: checked in the real window on the in-box conhost ConPTY (Windows 10 19045): prompt, colours, accents, Tab completion, split reflow and resize work, but a new Claude tab draws about 80 columns in a 95-column pane until the first resize, one prompt showed a run of spaces before the echoed input, and `€` echoes as `?` in the PSReadLine line (output correct). Next: `build/bundle-conpty` ships Microsoft's ConPTY (`conpty.dll` + `OpenConsole.exe`) next to `yien.exe`, which the app-dir search allows. On AMD GPUs gpui's bare-name load of `amd_ags_x64.dll` now fails and logs one error; the renderer still starts.
- `feat/agent-state-machine`: the per-pane hook token travels in the `YIEN_HOOK_TOKEN` environment variable (04 §2.4), never in the `--settings` file. Registered Claude events: the eight of 04 §2.4 plus `PostToolUse` and `PostToolUseFailure`, the real exits from a permission wait.
- `feat/agent-state-machine`: hooks use Claude Code's exec form (`"command": "<yien-hook.exe>", "args": ["<event>"]`), so no shell runs them and nothing depends on Git Bash or PowerShell. Since which Claude Code version first accepts `args` is unknown, S6 must check it against the 2.0 rule; `yien-hook` should read the event from the payload first.
- `feat/agent-state-machine`: a `PermissionRequest` carrying `agent_id` (a subagent) or with an unreadable payload never lights the red mark (RN-02); `agent_type` alone does not count, since a main session run with `--agent` carries it too. S6 must confirm with fixtures whether subagent requests show a dialog.
- `feat/agent-state-machine`: user input followed by output during the 300 ms confirmation window cancels the pending red, as it leaves a confirmed one.
- `feat/agent-state-machine`: OSC 9, OSC 777 and BEL never change the state: they cannot tell "done" from "waiting" (RN-02). Codex and OpenCode stay idle-only until S7 and S8.
- `feat/agent-state-machine`: diverges from 04 §4.7 ("se usa la última"): an unverified CLI version uses the newest rule (highest lower bound), not the last one listed; a rule without `versions` is never counted as verified (RF-AGE-11).
- `feat/agent-state-machine`: `regex` joins the layer-1 allowlist (plan §3.2).
- `feat/agent-state-machine`: diverges from 04 §4.5: a `SessionStart` with `source = compact` or `resume` during a turn keeps the state and the red mark; `startup`, `clear` and the rest go to Idle as 04 says.
- `feat/agent-state-machine`: a hook payload that is too large or malformed falls back to the event name `yien-hook` got in argv, with no payload fields (`decode_claude_hook_or_event`), instead of `Ambiguous`.
- `feat/agent-state-machine`, open: parallel tool calls (a `PostToolUse` from another tool clears a pending or confirmed red; S6 fixtures decide); no warning channel for unknown profile keys (plan §7.4); value errors in profiles name the field path, not the line; no `.yrec` fixtures for the Claude version ranges (RNF-23); Codex and OpenCode resume arguments unverified (S7, S8); Windows hook shell and quoting unverified (S6).
- `feat/core-panes`: the frame types (`Frame`, `Cell`, `Rgb` and the rest) moved from `yien-vt` to `yien_proto::frame` with serde; `yien-vt` re-exports them unchanged, so the UI can draw frames without `yien-vt`. `Frame` carries the terminal `Modes` (DECCKM, bracketed paste, mouse, focus reporting). `PROTO_VERSION` is 3.
- `feat/core-panes`: workspace actions are `yien_proto::Command` variants (ADR-19), wrapped in `ClientMsg::Command`; terminal traffic (input, reports, resize, scroll, selection, window focus) is a separate `ClientMsg` variant. The catalog has no titles or shortcuts yet (palette work).
- `feat/core-panes`: the core owns a 2-thread tokio runtime (`tokio 1.54.1`, already in the lock through gpui). Each pane is a task plus one reader thread; the engine sits behind one mutex the reader takes per chunk and the actor takes to copy a frame. Every PTY write goes through the actor's outbox in this order: VT replies, then a pending resize, then input; a refused write is retried every 5 ms. Every queue is bounded (plan §4.2): `ClientMsg::Input` and `Report` go from the handle straight to the pane's own queue (`PANE_INPUT_QUEUE`, 256), and the actor takes the next chunk only once the PTY accepted the last, so a program that stops reading makes `try_send` return `Busy` for that pane alone while commands (close, terminate) still pass. Control commands have a 256-slot queue the actor always drains; more than 64 unwritten replies stop the actor taking output, which stalls the child. Actors report to the service through a mailbox that keeps lifecycle events in order and only the latest state, title, directory, session id and selection between them, so a stalled UI cannot grow it.
- `feat/core-panes`: frames are "last one wins" (plan §4.2): each pane has one frame slot; the actor puts at most one frame per 8 ms while dirty and visible, and sends `CoreMsg::PaneFrameReady { pane }` only when the UI has taken the previous one; the UI calls `CoreHandle::take_frame(pane)`. A notice refused by a full event queue is sent as soon as there is room. Every other event waits for room. A pane in a hidden tab, or hidden by a maximized pane, publishes no frames.
- `feat/core-panes`: swap exchanges the core's leaf-to-pane mapping (no layout change, no respawn); `ResizeSplit` is `Tree::resize(pane, delta)`; `yien-layout` gained `Tree::shape()` so the layout reaches the UI as `LayoutNode`. Closing the last pane of a tab closes the tab; a split focuses the new pane.
- `feat/core-panes`: agent profiles launch their detected command; launch arguments and env vars that need a placeholder only the hooks pipe or session layer can fill (`{new_uuid}`, `{session_id}`, `{hooks_settings_file}`, `{hook_token}`) are left out, so Claude starts with no arguments for now. The CLI version is not probed, so the newest rule runs unverified.
- `feat/core-panes`: OSC 133 `B` (typing a command) has no agent meaning; `C` maps to the agent's command start and `D` to its end. `yien-vt` does not parse OSC 7501, so that source stays silent.
- `feat/core-panes`: the service keeps each pane's launch plan and last size, so relaunching a pane whose actor panicked starts a fresh actor at that size and view (§4.5, RF-PAN-19). Input still queued when a pane is relaunched or terminated is dropped with the old program. Every session runs on a fresh engine, so modes and screen of the last run do not leak and an old reader cannot feed the new one. A reader that dies before `Exited` ends the program and fails the pane with a message; the pane can be relaunched.
- `feat/core-panes`, open: frames are not a `CoreMsg`, so a future `--host` transport must carry them and fill the client side of `take_frame` (ADR-03); `Effect::Notify`, OSC 52 clipboard and the bell are not forwarded; tab branch is always `None` until `yien-git`; the only `tracing` event is a crashed actor's capped panic message; core tests run on real time (`FakeClock` is `!Sync`); `ResizeSplit` spreads the change over all siblings rather than one divider.
- `feat/agent-state-machine`, open: parallel tool calls (a `PostToolUse` from another tool clears a pending or confirmed red; S6 fixtures decide); no warning channel for unknown profile keys (plan §7.4); value errors in profiles name the field path, not the line; no `.yrec` fixtures for the Claude version ranges (RNF-23); Codex and OpenCode resume arguments unverified (S7, S8); `AgentState` not yet in `yien-proto`; Windows hook shell and quoting unverified (S6).
- `feat/hook-pipe`: the hook pipe server is the `yien_platform::hook_pipe` module, not a separate `yien-hooks` crate: plan §3.2 has no such crate, gives the IPC transport to `yien-platform`, and only `yien-pty` and `yien-platform` may use `unsafe`. `yien-hook` is a new layer-4 binary crate with no async runtime and no `unsafe`. It depends on `yien-proto` and on `yien-platform` for `hook_pipe::connect_client`, because checking the server's pid needs FFI and only `yien-platform` may hold it. The client opens the pipe with `SECURITY_ANONYMOUS`.
- `feat/hook-pipe`: the frame lives in `yien_proto::hook_frame`, hand-written with no dependency: magic `YH`, version 1, token length (1..=128), event length (0..=64, ASCII letters, digits, `_`), payload length u32 LE (≤ 4 MiB, pinned to `yien_agent::MAX_HOOK_PAYLOAD` by a test), then the bytes. The env variables are `YIEN_HOOK_PIPE` and `YIEN_HOOK_TOKEN`; `yien-hook` opens only a name of the exact shape the server makes (`\\.\pipe\yien-hook-<pid>-<16 lowercase hex>`, `hook_frame::hook_pipe_pid`), through `\\?\pipe\` so Win32 does not normalize it. A prefix check alone was bypassed with `..`, since Win32 resolves `..` inside `\\.\` paths, and let a tampered environment overwrite a file. It also requires `GetNamedPipeServerProcessId` to equal the pid in the name, so a process that takes the name after YIEN exits does not receive payloads.
- `feat/hook-pipe`: `yien-hook` does all its work on a thread and exits 0 after 1 s whatever happened, writing nothing to stdout or stderr. Stdin above 4 MiB is drained and sent as an empty payload, so the server falls back to the argv event.
- `feat/hook-pipe`: the server names each pipe `\\.\pipe\yien-hook-<pid>-<16 random hex>`, creates the first instance with `FILE_FLAG_FIRST_PIPE_INSTANCE` and always owns at least one instance afterwards (the next listening instance is created before a connected one is handed off; one that cannot be handed off is disconnected and reused), so the name is never free for someone else to create, uses `PIPE_REJECT_REMOTE_CLIENTS` and a protected DACL with one entry for the current user's SID. Overlapped I/O: one connection thread per client (at most 64; more are refused as busy), 2 s for the whole frame, reads cut short when the server is dropped, a 50 ms backoff after a failed connect, sizes checked before allocating and the token (256-bit, from `getrandom`, compared in constant time) before reading the payload. An authentic frame whose payload does not decode even with the argv fallback is still delivered, as an `Err`, so the core can feed it as `Signal::Ambiguous`. A client that connects, writes and closes before `ConnectNamedPipe` returns (`ERROR_NO_DATA`) is still read: its bytes are delivered if buffered, otherwise it counts as a truncated frame.
- `feat/hook-pipe`: outside Windows `HookPipeServer::start` returns `Unsupported` and `yien-hook` sends nothing; the end-to-end tests are Windows only. A unix socket comes with Linux and macOS support.
- `feat/session-store`: the state file is `workspace.json` (plan §7.2), with backups `workspace.1.json` to `workspace.4.json`: five copies in all (RF-SES-06). `save` rotates only when the snapshot is `ROTATION_INTERVAL_MS` (60 s) past the one in `workspace.1.json`; other saves replace `workspace.json` atomically. A damaged `workspace.json` is moved to `workspace.damaged.json` for diagnosis, leaving the backups untouched.
- `feat/session-store`: a generation with a newer `schema_version` stops `load` without restoring and makes `save` refuse; `preserve_newer` renames it to `workspace.v<N>.json` (plan §5.2), after which saving works.
- `feat/session-store`: split ratios are checked as positive, one per child and summing to 1 (within 1e-3), but not against `yien-layout`'s 5 % minimum, because repeated splits legitimately go below it.
- `feat/session-store`: schema v1 carries every plan §6.1 field before it ships: `selected` (project and tab, both optional, validated to exist), tab `branch`, `worktree` and `archived`, pane `name`, project `setup_script`. All have serde defaults, so a v1 file without them still loads.
- `feat/session-store`: file I/O goes through the `Store` trait; the `fs` feature's `FsStore` uses only `std::fs` (temp file, `sync_all`, `rename`) and lacks `MOVEFILE_WRITE_THROUGH`, so `yien-platform` should supply the production store.
- `feat/session-restore`: the state files live in `<data dir>/state/` (plan §7.1, 04 §4.6), not in the data dir itself as the TASK said, so logs, hook settings and state stay apart; `YIEN_DATA_DIR` still redirects all of it.
- `feat/session-restore`: the core owns persistence. `CoreConfig::session` (a `SessionStore` over any `yien_session::Store`) is loaded off the runtime before the first `WorkspaceSnapshot`; a writer thread owns the store and writes the newest `to_session()` 250 ms after the last change (plan §7.1), at most 2 s after the first unsaved one (RNF-09), skipping snapshots equal to the last. `CoreHandle::save_session(timeout)` is the quit save: it writes on its own thread, the caller waits at most the timeout (the app uses 1.5 s), and every change after it is ignored, so programs dying as the app exits never reach the file. Nothing is saved before the restore finishes. `saved_at` comes from the system clock.
- `feat/session-restore`: `yien-layout` gained `Tree::from_shape`, since `split` flattens same-orientation branches and always halves, so it cannot rebuild a saved tree with its ratios. `yien-session` gained `impl Store for Box<S>`, so a store chosen at run time goes through `save` and `load`.
- `feat/session-restore`: a restore keeps every saved id and continues numbering after the highest. `yien-session` refuses ids above `MAX_ID` (`u32::MAX`), and the core's id counter fails the command (`CoreError::OutOfIds`) rather than wrap, so a damaged file can never make a new pane reuse a live id. The maximized pane is not in the schema, so a restored tab is never maximized. A saved session with no tabs counts as none, so closing every tab does not leave the next start empty. A tab whose layout cannot be rebuilt is left out with a notice; an unknown profile opens the shell with a notice; a pane or tab folder that no longer exists falls back to the project root, then home, with one notice listing the missing folders (RF-SES-12). Restore notices share the status bar's single notice line with the hooks notice.
- `feat/session-restore`: fallbacks are for the launch only. A pane launched in another folder or with the shell keeps its saved folder, profile and agent record, and saves those again until it reports a folder other than the one it was started in; a tab keeps its saved folder the same way. So an unmounted drive or an uninstalled profile loses nothing. An agent pane whose folder is missing is not resumed elsewhere: a new session starts in the fallback folder, the saved one stays recorded, and the notice says so.
- `feat/session-restore`: when the start loaded a session but did not restore all its tabs, or loading itself failed, `workspace.json` is renamed to `workspace.unrestored.json` before the first save (replacing an earlier one), with a notice; if that rename fails, nothing is saved in that run. Without this the fresh workspace would replace a good file, since backups only rotate once a minute.
- `feat/session-restore`: a session counts as ended by the user (RN-04, `ended_explicitly`) on a `SessionEnd` hook with reason `prompt_input_exit` or `logout`, and on `TerminatePane`; `clear`, `resume` and `other` do not (YIEN stopping Claude sends `other`). A new session id clears it. With hooks off, `/exit` is not seen, so that session is resumed at the next start: a known limit.
- `feat/session-restore`: only the first launch after a restore resumes (`--resume {session_id}` from the profile's `launch.resume`, with the hook settings and token as for a new launch); a relaunch or a crashed actor starts a new session. The restored pane keeps the saved session id until the resumed program reports one, so a quick quit does not lose it.
- `feat/session-restore`: the start folder rule is `yien_platform::paths::pick_start_dir` (pure): the current folder, unless it is `%SystemRoot%`, its `System32` or `SysWOW64`, or the folder holding `yien.exe`, compared without case, separator, trailing separator or `\\?\` prefix differences; then home. The exe folder is refused however YIEN was started, since a double-click cannot be told apart.

- `feat/git-info`: `yien-git` runs the `git` CLI, not `gix`: no new dependencies (only `thiserror` and `tracing`), no compile cost on this RAM-limited machine, nothing new for `cargo deny`, and porcelain v2 is a format git keeps stable for scripts. Needs git 2.31+ (`rev-parse --path-format`); listing the main worktree of a linked one uses `worktree list --porcelain -z` (2.36+) and degrades to `None` on older git.
- `feat/git-info`: execution model. A repository is untrusted, so no git call may start a program it names. Closed on every call: transports (`protocol.allow=never` plus `protocol.<name>.allow=never` for `file`, `ssh`, `git`, `http`, `https` and `ext`, because a repo-local `protocol.<name>.allow` beats `protocol.allow` and only command scope beats the repo; empty `core.sshCommand`, `credential.helper`, `core.askPass` and the `GIT_SSH*`/`*ASKPASS` env), lazy fetch in a partial clone (`GIT_NO_LAZY_FETCH=1` on git 2.44+; on older git, which ignores it, the per-protocol denials alone stop the fetch, tested with the variable removed), fsmonitor (`core.fsmonitor=false`), and writing the index or refs (`--no-optional-locks`, `GIT_OPTIONAL_LOCKS=0`), so no hook can fire. Closed for `status`: content filters from any scope but global, system and command, emptied with `-c` (an unexpressible key is `GitError::UnsafeFilter`). The rest is unreachable: `rev-parse`, `status --porcelain` and `worktree list` use no pager, editor, diff or textconv driver, merge driver or GPG, and with transports closed nothing reaches the network. What remains: filters in the user's own global and system config run (git-lfs keeps working); on Windows a timeout kills git but not processes it started. Inherited `GIT_DIR`/`GIT_WORK_TREE`/`GIT_INDEX_FILE` and similar are removed; `LC_ALL=C`; no console window; 2 s timeout; stdout capped at 32 MiB; `status --ignore-submodules=dirty`. A repository owned by another user is `GitError::UnsafeRepository { path }`, so the UI can offer `git config --global --add safe.directory <path>`.
- `feat/git-info`: the changed-file list folds staged and unstaged changes into one status per file (conflicted, renamed or copied, added, deleted, else modified); untracked files count as dirty; ignored files are left out. Paths that are not UTF-8 are shown with replacement characters.
- `feat/git-info`: `GitWatcher` polls, with no `notify`: every 500 ms it reads HEAD's content and the size and mtime of the index, the current branch's loose ref, `packed-refs` and `FETCH_HEAD`, and reports `Change::Git` one interval after they settle (the first poll that sees them unchanged). Work tree edits leave the git directory untouched, so it also fires `Change::Refresh` every 5 s; the consumer re-runs `status` on either. One watcher for the active tab; dropping it stops the thread.
- `feat/git-info`, open: a push (which updates `refs/remotes/*` but not `FETCH_HEAD`) shows its new ahead count only at the next refresh.
- `feat/terminal-view`: the UI reaches the core through a `CoreClient` trait the binary implements over `CoreHandle`, and reads events from the core's tokio receiver on GPUI's executor (`yien-ui` gains `tokio` with `sync` only). A busy core never drops input silently: the UI queues messages in order, up to 64 KB per pane and 1024 shared messages, and retries from 5 ms backing off to 250 ms, stopping when every queue is empty. A pane with a backlog says "Not reading input"; a full one refuses new keys and says so, and mouse motion to it is dropped. The status bar says when the core is busy.
- `feat/terminal-view`: printable text reaches a pane only through GPUI's input handler (WM_CHAR, IME, AltGr, dead keys); key-down handles named keys and Ctrl/Alt combinations and stops propagation, which on Windows suppresses the WM_CHAR. Keys with `prefer_character_input` (AltGr) are always text.
- `feat/terminal-view`: rows are shaped in runs of equal style with GPUI's forced cell width; every wide character is its own two-cell run. Cell size comes from the mono font's advance and ascent plus descent at 13 px, snapped to device pixels (RNF-19).
- `feat/terminal-view`: tab selection goes through `Command::SelectTab`, since the core sends frames only for the active tab. Closing the window quits the app so the core's panes end.
- `feat/terminal-view`: shortcuts follow Windows Terminal and the prototype: Alt+Shift+= / Alt+Shift+- split, Ctrl+Shift+W closes, Alt+arrows focus, Alt+Shift+arrows grow or shrink within the pane's split, Ctrl+Alt+Shift+arrows swap, Ctrl+Shift+Enter maximizes, Ctrl+Shift+C/V copy and paste.
- `feat/terminal-view`: input and reports wait in one retry queue per pane, so a pane whose program stops reading never holds up the others; frames are taken from the core on `PaneFrameReady` and for every visible pane when the layout or the selected tab changes. Paths and branches are drawn in the mono family: the Japanese UI faces draw a backslash as a yen sign.

Application keypad mode (DECKPAM, `Modes::app_keypad`) is ignored: GPUI on Windows does not name numpad keys apart from the main ones, so numpad digits and operators always send their characters.
